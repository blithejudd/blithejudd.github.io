# ZUKA GULIEVI — портфолио фотографа

Существующий сайт обновлён без React, npm-зависимостей и обязательной сборки: HTML, CSS, ES-модули JavaScript. Публичный сайт — на грузинском, панель владельца — на русском. Хостинг: GitHub Pages, домен `gulievi.me`. Данные, вход и фотографии: Supabase REST API.

## Быстрый локальный просмотр

Требуется Node.js 22+ (тестировалось на Node.js 26).

```powershell
node D:\blithejudd.github.io\scripts\serve.mjs
```

- Сайт: http://127.0.0.1:4173/
- Панель: http://127.0.0.1:4173/admin/
- Остановка: Ctrl+C. Не открывайте HTML через `file://`: ES-модулям нужен HTTP.

До настройки Supabase показываются шесть уникальных существующих фотографий. Админка объясняет настройку и не имитирует вход/сохранение. Контактная форма отключена, ссылка на Instagram работает независимо от backend.

## Сначала: отозвать старый Telegram-токен

В прежней версии публичного JavaScript находился токен бота. **Отзовите его через BotFather и создайте новый.** Удаление из текущего файла не удаляет токен из Git-истории и кэшей. История намеренно не переписывалась. Новый токен хранится только в Supabase Secrets.

### Вход владельца сейчас

1. Откройте локальный файл **`C:\Users\Dato\Gulievi-admin-access.json`**: поля `email` и `password` — ваши временные данные. Файл находится вне репозитория; доступ Windows ограничен текущим пользователем. Не отправляйте его в чат и не загружайте на сайт.
2. Войдите на **https://gulievi.me/admin/**.
3. Откройте **«Настройки входа — сменить пароль»**, укажите текущий пароль и дважды новый (минимум 12 символов). Сохраните новый пароль в менеджере паролей, затем удалите локальный файл с временными данными.
4. Сгенерированный адрес `@example.com` — только временный логин, не почтовый ящик. Доставка писем и восстановление через него невозможны. Настоящую почту можно привязать позже через Supabase → Authentication → Users; функция смены email в сайте пока не добавлена, чтобы не обещать непроверенную доставку/подтверждение.

`scripts/owner-access.mjs create` отказывается создавать владельца поверх существующих пользователей. `test` выполняет реальные операции на одноразовых фото/аккаунте, затем очищает их; не запускайте одновременно с проверками количества опубликованных фотографий.

**Безопасность:** секретный ключ Supabase, раскрытый в переписке, необходимо отозвать и заменить в Dashboard → Settings → API Keys. Он не добавлен в проект и не использовался для проверок. Новый секретный ключ не присылайте; для GitHub Pages нужны только публичные параметры. JWKS URL вручную настраивать не требуется.

1. Создайте **новый отдельный проект** на https://supabase.com/. Учитывайте актуальные лимиты хранения, трафика и возможную приостановку бесплатного проекта. Не применяйте эту схему к чужому/общему проекту с существующими открытыми политиками.
2. Откройте SQL Editor и выполните содержимое `D:\blithejudd.github.io\supabase\schema.sql`. Оно создаст таблицы, RLS, публичный bucket `portfolio` и шесть записей для фотографий, уже лежащих на сайте.
3. Authentication → Providers / Sign In: оставьте Email и **выключите Allow new users to sign up** (названия разделов могут меняться).
4. Authentication → Users → Add user: создайте email/пароль владельца, подтвердите email (Auto confirm). Используйте длинный уникальный пароль. Пароль не записывается в код и не отправляется разработчику.
5. Скопируйте UUID пользователя. В SQL Editor выполните запрос ниже, подставив этот UUID вместо `UUID_ВЛАДЕЛЬЦА`:

```sql
insert into public.portfolio_admins (user_id)
values ('UUID_ВЛАДЕЛЬЦА'::uuid)
on conflict do nothing;
```

6. Settings → API / API Keys: скопируйте Project URL и **Publishable key** (`sb_publishable_...`). Legacy `anon` также поддерживается. **Никогда не используйте service_role или sb_secret в браузере.**
7. В `D:\blithejudd.github.io\js\config.js` заполните `supabaseUrl` (без завершающего `/`) и `supabaseKey`. Это публичные параметры; безопасность обеспечивает RLS и таблица владельцев, а не сокрытие ключа.
8. Authentication → URL Configuration: Site URL `https://gulievi.me`. Публичной регистрации, восстановления пароля и email-redirect flow в интерфейсе нет. Восстановление доступа выполняется владельцем проекта через Dashboard.
9. Перезапустите страницу `/admin/` и войдите. Проверьте загрузку **сначала черновика**, затем публикацию. Откройте сайт в приватном окне и убедитесь, что черновик не показан.

Наличие аккаунта Supabase не делает человека администратором. Только UUID в `portfolio_admins` имеет право изменять фотографии/Storage. Таблица администраторов недоступна браузерным ролям. Не добавляйте широкие политики `authenticated = allow all`.

### Работа с фотографиями

- «Добавить фото»: выбор или перетаскивание до 12 файлов JPG/PNG/WebP, до 20 МБ каждый. HEIC следует предварительно экспортировать в JPG.
- Браузер последовательно уменьшает фото до 2400 px по длинной стороне, кодирует WebP, не переносит EXIF. Серверный bucket принимает только WebP до 8 МБ. Фото свыше 80 Мп отклоняются после декодирования; на старом телефоне лучше выбирать небольшие партии.
- Для каждого фото: название, доступное описание, категория, порядок и переключатель «Опубликовано». Тексты показываются посетителям без перевода — для сайта пишите по-грузински.
- Меньшее число порядка выводится выше; одинаковые значения стабильно сортируются по UUID. Изменения становятся видны после перезагрузки сайта.
- **Черновик скрывает запись из галереи, а не файл из публичного Storage.** Прямая ссылка продолжает работать. Не загружайте приватные клиентские съёмки. Для них нужна отдельная закрытая галерея с private bucket.
- Удаление сначала убирает запись, затем файл. Если удаление файла не удалось, панель покажет путь для ручной очистки Storage. При неопределённом результате сетевого запроса сначала нажмите «Обновить»: запись могла сохраниться; не повторяйте загрузку вслепую.
- Исходные фото имеют тип `local`: удаление убирает запись галереи, но не файл из GitHub. Главный портрет и фото «О фотографе» остаются статичными в `index.html` и не управляются панелью.
- Сессия хранится в `sessionStorage` текущей вкладки, обновляется перед запросами. Кнопка «Выйти» отзывает refresh-сессию. Уже выпущенный access JWT может действовать до истечения срока; при компрометации немедленно удалите UUID из `portfolio_admins` и отзовите сессии в Dashboard.
- После подключения БД является единственным источником галереи. При сбое Supabase показывается ошибка с повтором, **не** прежние локальные фото: скрытые/удалённые работы не воскресают.

## Заявки в Telegram — необязательное отдельное подключение

Для галереи и админки этот шаг не нужен. Пока форма выключена, посетитель может написать в Instagram.

1. После отзыва старого токена создайте новый в BotFather; напишите боту со своего Telegram-аккаунта и получите свой chat ID. Не коммитьте эти значения.
2. В Supabase Edge Functions → Secrets добавьте:
   - `TELEGRAM_BOT_TOKEN` — новый секретный токен;
   - `TELEGRAM_CHAT_ID` — получатель;
   - `CONTACT_HASH_SALT` — длинная случайная строка (не менее 32 символов);
   - `ALLOWED_ORIGINS` — `https://gulievi.me,https://blithejudd.github.io` (для локальной проверки временно добавьте `http://127.0.0.1:4173`).
3. Разверните функцию `contact` из `D:\blithejudd.github.io\supabase\functions\contact\`, включая оба файла `index.ts` и `validation.js`. `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` доступны внутри Edge Functions автоматически.
4. Если используете установленный Supabase CLI, из папки проекта выполните:

```powershell
supabase login
supabase link --project-ref ВАШ_PROJECT_REF
supabase functions deploy contact --no-verify-jwt
```

Команды требуют вашего аккаунта; агент их не выполнял. Функция публичная, поэтому `verify_jwt = false` намеренно: у посетителя нет аккаунта. Защита: строгая валидация, лимит фактического тела 16 КБ, honeypot, квоты в БД (3 попытки/контакт/час и 30 глобально/час), allowlist Origin. Origin сам по себе **не является аутентификацией**. При заметном спаме добавьте серверно проверяемую CAPTCHA; текущий глобальный лимит может быть исчерпан злоумышленником.

5. После успешного развёртывания включите `contactEnabled: true` в `js/config.js`.
6. Отправьте тестовую заявку, убедитесь, что она пришла в Telegram. Ответ об успехе выдаётся только после `ok: true` от Telegram. Повтор после сетевого таймаута может создать дубликат сообщения.

Заявки не сохраняются в БД, а пересылаются в Telegram. В БД временно хранятся только счётчики и хеш контакта с солью; очистка старых записей выполняется при следующей заявке. Текст согласия в форме нужно проверить на соответствие вашей политике обработки персональных данных.

## Проверки

```powershell
powershell -ExecutionPolicy Bypass -File D:\blithejudd.github.io\scripts\verify.ps1
node D:\blithejudd.github.io\tests\browser.mjs
```

Браузерные тесты запускают установленный Chrome headless через CDP без npm-библиотек. Если Chrome находится в другом месте, задайте `CHROME_PATH`. Порт 4173 должен быть свободен. Скриншоты сохраняются в `test-results/` (не коммитятся).

Проверяются фильтры, лайтбокс, мобильное меню, размеры 320/390/768/1440, настройки админки, XSS-безопасный вывод и сценарии API через mock transport: вход владельца/отказ другому пользователю, сохранение, WebP-загрузка, черновики, удаление, выход, контактная форма и сбой backend. **Mocks не доказывают корректность развёрнутого RLS, Storage и Telegram.**

### Обязательный live-чек-лист после настройки

- [ ] В приватном окне видны только опубликованные работы.
- [ ] Без авторизации прямые POST/PATCH/DELETE в `photos` и upload/delete в Storage отклоняются.
- [ ] Аккаунт, которого нет в `portfolio_admins`, не может изменять данные через прямой API.
- [ ] Владелец загружает, публикует, меняет порядок и удаляет фото с телефона.
- [ ] Перезагрузка и обновление access token не теряют доступ, выход закрывает панель.
- [ ] При отключении интернета показывается ошибка, а не ложный успех.
- [ ] Реальная заявка приходит в Telegram; неверные/слишком частые запросы отклоняются.
- [ ] Проверьте iPhone Safari / Android Chrome, грузинские формулировки, действительность цен и согласие клиентов на публикацию фото.
